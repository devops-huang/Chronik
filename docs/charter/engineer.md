## 4. 低估陷阱识别（PM 估小了的地方）

### 4.1 P0-4 分享卡片 —— 最大陷阱（S-M → 实际 L）

PRD 说"成本近乎为零、复用已有资产"。**不成立。** 现状是**零构建纯静态 + 依赖仅 `pg` + `cantian-tymext`，项目中不存在任何服务端图形库**：

- 服务端生成中文长图必须引入新依赖：`@resvg/resvg-js` / `sharp`（原生二进制，需验证目标服务器 glibc 与内存）或 Puppeteer（无头 Chromium，这台既有小内存服务器很可能扛不住）。**这本身就是 1–2 天的选型试错，且是部署风险，不是功能风险。**
- 字体：全站自托管 Cinzel / Cormorant / 马善政**子集**。子集意味着**生僻字大概率缺字**，命理内容又常出现生僻字 → 需要补字子集或回退策略。
- 中文断行、竖排、长图高度自适应 —— 手绘 canvas 布局是众所周知的工时黑洞。
- **OG 图的隐藏合规风险**：OG 图需要一个可公开访问的 URL。若 URL 含命盘 id，`/api/charts/:id` 会返回完整八字 → **任何人拿到分享链接就能看到他人完整命盘**。必须做签名 token + 脱敏（只放三句话总结，不放四柱）+ 随机不可遍历 code。PRD 完全没提。
- **降级方案（我建议采纳）**：做「文案卡片」——纯 DOM 渲染的品牌卡（三句话总结 + 品牌名 + 短链 + 免责小字），提供"复制文案"和"保存图片（调用浏览器原生截图或 html2canvas 自托管一份）"。**0.5 人日，拿到 80% 的传播价值。** 真正的服务端 PNG 放 P1。

### 4.2 P0-6 配额体系 —— 看着是加个 `if`，实际是改核心链路

- 现有 `anon_chart_rate` / `anon_chat_rate` 是**限流**（防刷），语义与**配额**（按天额度）完全不同，不能复用，需新增 `usage_daily` 或改造。
- **时区坑**：PG `now()` 是 UTC，中国用户要"自然日"。`date_trunc('day', now() AT TIME ZONE 'Asia/Shanghai')` 与前端"我的剩余额度"显示必须一致，否则用户看到"还有 3 次"但服务端说 0 次 → **直接引发投诉，且这是付费产品**。
- **并发扣减竞态**：无 Redis，只能靠 PG `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子递增，单人开发极易先写 SELECT 后 UPDATE 的竞态版本。
- **三态用户**：游客（anon_id）/ 注册免费（user_id）/ 付费（plan + expires_at）/ **付费过期**。第四态最容易漏，漏了就是"付费用户到期后仍能免费用"或"付费用户被误拦"（后者 = 直接退费投诉）。
- **回归面 = 全站核心**：`/api/chat` 是全站最复杂的 handler（SSE + 会话 + 内容策略 + LLM 兜底），在它上面动刀，风险等级最高。

### 4.3 P0-9 合规话术固化 —— "统一追加后缀"在 SSE 下不成立

流式输出要追加免责声明，必须在流结束时写入，且前端要能区分"AI 生成内容"与"系统后缀"，否则会被拼进引用气泡或被 `marked` 二次渲染。另外 PRD 要求"命中即**改写**"——改写意味着二次 LLM 调用，成本翻倍 + 延迟翻倍，**实际只能做"拦截 + 固定话术"**，请 PM 把验收标准改成拦截。

### 4.4 其他

- **P0-1**：2 处文案（PRD 只写了 1 处），且真正的交付物是发布检查清单，不是改文案。
- **P0-7**：人工收款不是"零成本"，是**把开发时间换成运营时间**。30 笔 = 30 次人工核对 + 发码 + 对账，且承诺 ≤12 小时响应 → 这是持续 90 天的时间债，会**反向吞噬 B2/B3 的开发时间**。这是 PRD 完全没计入的成本。
- **P1-3 深度报告**（虽属 P1）：PM 估 M，我估 **L（8–10 人日）**——新报告模板 + 长文 LLM 生成 + 四段结构化 + 逐段合规校验 + 长文本超时 + 单次可能 5k+ token 的成本。这是 P1 里最贵的项，别当 M 排。

## 6. 质量保障建议（最小可行 · 拒绝过度工程）

**现状（好消息）**：`tools/` 下已有 `smoke` / `test-auth` / `test-chart` / `test-report` / `test-pipeline` / `test-content-policy` / `test-gdpr` / `qa-gates` 共 8 个可用脚本。**基础设施已经够了，问题是它们没被串进发布流程，单人开发容易漏跑。**

**建议只有 4 条，总计 ≤2.0 人日，摊进各批次：**

1. **一条命令的发布门禁（0.3d，B1 前做完）**
   `npm run preflight` = 串联 smoke + test-auth + test-chart + test-report + test-content-policy + test-gdpr，任一红即不许发版。**这是投入产出比最高的一项**，因为现在脚本已有、只是没人跑。
2. **为付费/配额链路补 3 个针对性脚本（1.2d，随 B2 写）**
   - `test-quota.mjs`：免费层用尽是否被拦 / 付费层是否放行 / **跨自然日是否重置** / 付费过期是否正确降级
   - `test-redeem.mjs`：重复兑换 / 已用码 / 过期码 / 兑换后 plan 与 expires_at 正确
   - `test-paywall.mjs`：**绕过前端直连 API 是否被服务端拦住**（这是 PRD 验收标准"前端限制不算数"的唯一验证手段，必须做）
3. **发布检查清单（0.2d，P0-1 的交付物）**
   `docs/RELEASE-CHECKLIST.md`，10 条，含"文案⇄实现一致性"逐项核对 + 配额/付费手工回归 5 步。**个人产品没有 QA，这是唯一可行的防线**（PRD §6 自己已指出）。
4. **每日 `pg_dump` 备份（0.3d，必须在动 `users` 表之前）**
   保留 7 天。`users` 表要加 `plan` / `plan_expires_at`，一次误操作 = 用户与收入数据全丢，且单人无回滚能力。

**明确不做**（ROI 为负）：单元测试框架（Jest/Vitest）、CI/CD、Playwright E2E、覆盖率门禁、TypeScript 迁移。这套东西在单人业余项目上会把 20 人日预算吃掉 30%。

**一条关键架构建议**：所有新增的配额/付费查询必须包 `try-catch` 且 **fail-open（失败放行）**。单进程单体下，一次未捕获异常 = 全站挂；宁可少收一次钱，不可让免费用户也用不了。**P0-6 的失败模式设计比正常路径更重要。**
